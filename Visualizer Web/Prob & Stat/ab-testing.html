01 Correlation ≠ causation — และ Simpson's paradox

สังเกตว่า “คนดื่ม Diet Coke อ้วน” → (A) Diet Coke ทำให้อ้วน หรือ (B) คนอ้วนชอบดื่ม Diet Coke? ดูแค่ข้อมูลเชิงสังเกต (observational data) ตอบไม่ได้ ว่าอันไหนเป็นเหตุ ต้องทดลองแบบสุ่ม

Story 1 (สไลด์): “The Bad / Bad / Good Drug” — ยาแย่สำหรับผู้หญิง แย่สำหรับผู้ชาย แต่รวมกันแล้ว “ดี”?

ตัวแปรที่มีผลทั้งต่อตัวแปรต้น (ได้ยาหรือไม่) และตัวแปรตาม (heart attack) เรียกว่า confounder — ในที่นี้คือเพศ: ผู้ชายเสี่ยง heart attack สูงกว่า และอยู่กลุ่ม control เยอะกว่า

02 ทำไมต้อง A/B test — จัดการกับความสุ่มในการตัดสินใจทางธุรกิจ

ธุรกิจตัดสินใจกันอย่างไร

  • Realistic assumptions, scientific methods ✓

03 ① Define relevant metrics — build intuition about your system

Relevance vs vanity

Funnel: Home/Search/Listing → Product page (variation อยู่ตรงนี้) → Add-to-cart → Checkout → Payment
Relevant: conversions, add-to-cart rate, checkout rate · Vanity: clicks / CTR, page views — ดูดีแต่ไม่ได้บอกว่าขายได้มากขึ้น

Assumed distributions

Frequentist test ต้องรู้ variance ของข้อมูล:
Bernoulli — event probability (ซื้อ/ไม่ซื้อ) · Exponential — average revenue per user, average position clicked · Normal / Student t — ส่วนสูง น้ำหนัก คะแนน measurement error · ต้อง i.i.d. ด้วย — plot ดูก่อนเสมอ

Granularity — metric ส่วนใหญ่คือ event probability = # event / # หน่วย แต่ “หน่วย” เลือกได้หลายแบบ:

Event probabilityข้อดี / ปัญหา
# checkout / # hitsนับซ้ำเมื่อ refresh หน้า
# checkout / # sessionsนับซ้ำ visit ที่ไม่ active (timeout 15–30 นาที) · ดีถ้าอยากรู้ว่าสินค้าไหนซื้อได้ในไม่กี่ visit
# checkout / # cookiesใช้ “users” เป็นตัวหาร รวมทั้งคนล็อกอินและไม่ล็อกอิน · คนเดียวหลาย browser/device นับซ้ำ
# payment / # cookiesนับเฉพาะการซื้อที่สำเร็จจริง
# payment / # user IDsคนไม่ล็อกอินทั้งหมดนับเป็น 1 user
# payment / # peopleอุดมคติ แต่ “people” คือใคร วัดไม่ได้

Attribution period — ลูกค้าหนึ่งคน journey ยาวแค่ไหน

ตัวอย่างสไลด์: cookie เดียว เข้า Home → Product (วันที่ 1), Search → Product (วันที่ 4), Product → Purchase (วันที่ 6) · metric = # payment / # cookies ต่อ X วัน

e-commerce (Amazon) จบใน 1 วัน · ตั๋วเครื่องบิน (Air Asia) หลายวัน · สมัครงาน (LinkedIn) เป็นสัปดาห์–เดือน → plot ระยะ journey จริงก่อนเลือก window · event-based (conversion ใน ส.ค. / คนเข้าใน ส.ค.) vs cohort-based (conversion ภายใน X วัน / คนที่เข้าใน ส.ค.)

Robustness vs sensitivity

สถิติสรุป (เช่น latency ของ YouTube) ต้องไม่เปลี่ยนสำหรับของที่เหมือนกัน (robust — median ทนค่าโดด) แต่เปลี่ยนสำหรับของที่ต่างกัน (sensitive — mean/p90 จับหางได้) → ลองกับข้อมูลจริงทั้งสองแบบ

Tasks ต่างกัน วัดต่างกัน

Recommendation ซื้อครั้งถัดไป → optimize purchase within session · แจ้งสิทธิประโยชน์สมาชิก → retention เดือนหน้า · แนะนำของขวัญวันพ่อ → purchase เดือนหน้า · ระวัง features vs targets และ target หลายตัวขัดกัน

Design journal (Sunflower): Metric = # payment / # cookie-days — แต่ละ cookie คือ Bernoulli trial → metric เป็น normalized binomial

04 ② Split samples into comparable groups

Split independently

  • Test ต้องการข้อมูล i.i.d. — hits / sessions มักไม่อิสระ เพราะคนเดียวอาจถูกนับทั้งในกลุ่ม control และ test
  • Hits: วัด usability (เปลี่ยนเมื่อ refresh) · Sessions: ไม่เปลี่ยนในหนึ่ง session · Cookies: “user” เดิมเห็นแบบเดิมเสมอ · User IDs: เข้มกว่าแต่ใช้กับคนไม่ล็อกอินไม่ได้
  • แบ่งที่ granularity ใหญ่กว่าที่วัด (แบ่ง cookie แต่วัด hit) → ต้องใช้ sample มากขึ้นเพื่อ power เท่าเดิม
  • อย่าให้กลุ่มมีปฏิสัมพันธ์กัน (ฟีเจอร์โซเชียล)

Control for X

  • Simpson's paradox — ต้องคุม confounder
  • ที่มาของ traffic เป็น confounder: คนมาจาก Search ตั้งใจหาเมล็ดทานตะวัน (conversion สูง) คนเข้าตรงอาจมาจาก ads (conversion ต่ำ) → เก็บ traffic source แล้ว A/B test ภายในแต่ละ source
  • Frame fairly: UI ใหม่ (ย้ายคอมเมนต์ไปด้านบน) ผู้ใช้อาจหาไม่เจอ → บอกผู้ใช้
  • Multiple experiments: ถ้ารันทดลองราคา/ฟอนต์ไปพร้อมกัน ต้องให้กระจายเท่ากันทุกกลุ่มสี ไม่งั้นแดงอาจชนะเพราะได้ราคาถูกกว่า

50/50 vs 80/20 — 50/50 ใช้เวลาสั้นกว่าแต่เสี่ยงกว่า (ถ้า B แย่ เสียครึ่งหนึ่ง) · 80/20 เสี่ยงน้อยแต่ต้องรันนานกว่า เพราะกลุ่มเล็กเป็นตัวจำกัด power — ลองดูจำนวนตัวอย่างรวมที่ต้องใช้:

สูตรในสไลด์: n = ((m + 1)/m)·((zα + zβ)σ/MDE)² ต่อกลุ่มใหญ่ โดย m = อัตราส่วนกลุ่ม (1 = 50/50, 2 = 33/67)
Design journal: 50/50 split บน cookies · รัน test แยกสำหรับ cookies ที่มาจาก direct traffic

05 ③ Choose statistical tests & validate assumptions

Frequentist hypothesis test กำลังพูดว่า…

สมมติว่า สิ่งที่เราเชื่อเป็นจริง (H₀: conversion ไม่ต่างกัน) → โอกาส (p-value) ที่จะเห็นค่าเฉลี่ยตัวอย่างสุดโต่งกว่า ที่เห็นอยู่ตอนนี้ (Z score) นั้นน้อยกว่า false positive rate ที่เรายอมรับได้ (statistical significance; 1%, 5%, 10%)

    ทางเลือกด้านเดียว (more vs less) มี threshold ของ Z ไม่สุดโต่งเท่า two-tailed เพราะดูหางเดียว (1.645 vs 1.96 ที่ α = 5%) — ต้องเลือกก่อนเห็นข้อมูล

    สิ่งที่ p-value ไม่ได้บอก (misuse of p-values)

    • ไม่ใช่ความน่าจะเป็นที่ H₀ จริง หรือที่ HA ผิด
    • ไม่ใช่ความน่าจะเป็นที่ผลเกิดจากความบังเอิญล้วน ๆ
    • 0.05 เป็นแค่ “ธรรมเนียม”
    • ไม่ได้บอกขนาดหรือความสำคัญของผล (n ใหญ่มาก ผลจิ๋วก็ significant)
    • ไม่ใช่ false positive rate ที่สังเกตได้ — ขึ้นกับ prevalence (base rate) ของการเปลี่ยนแปลงที่ได้ผลจริง
    Design journal: ใช้ one-tailed Z test ที่ significance 5%

    06 ④ Decide on stopping criteria — Minimum Detectable Effect & power

    “Test แบบ frequentist ส่วนใหญ่จะ significant ถ้ารันนานพอ” — Z = (X̄ − μ)/(σ/√n) โตตาม √n: variance สูง ทำให้เห็นความต่างยาก, n มาก ทำให้เห็นง่าย → ต้องกำหนดก่อนว่าความต่างเล็กสุดที่ “มีความหมายทางธุรกิจ” (MDE) คือเท่าไร แล้วคำนวณ n ที่พอดี

    Back-calculate sample size ต่อกลุ่ม (สไลด์) — pooled variance เท่ากัน, m = split ratio

    1. Φ−1(1 − α) = zα , Φ−1(1 − β) = zβ
      α = false positive rate (confidence = 1 − α), β = false negative rate (power = 1 − β)
    2. ใต้ H₀: Zcritical = μH0 + zα√(σ²(1/n + 1/mn)) = 0 + zα√(σ²(1/n + 1/mn))
      μH0 = 0 (ไม่ต่างกัน) · variance ของผลต่างค่าเฉลี่ยสองกลุ่ม
    3. ใต้ HA: Zcritical = μH1 − μH0 − zβ√(σ²(1/n + 1/mn)) = MDE − zβ√(…)
      เส้นเดียวกันต้องตัดหาง β ของ HA พอดี
    4. zα√(σ²(1/n + 1/mn)) = MDE − zβ√(σ²(1/n + 1/mn)) ⇒ zα + zβ = MDE√(σ²(1/n + 1/mn))
      ตั้งสองสมการเท่ากัน
    5. (m + 1)σ²mn = (MDEzα + zβ)² ⇒ n = m + 1m((zα + zβ)σMDE)²
      1/n + 1/mn = (m + 1)/(mn)
    6. n = 2((zα + zβ)σMDE)² ; m = 1
      split 50/50 · ถ้าตั้ง power = 50% → zβ = 0
    7. ตัวอย่างสไลด์: p = 10% → σ² = p(1−p) = 0.09 , MDE = 0.01 , z0.05 = 1.645 , z0.2 = 0.842 ⇒ n = 2(2.486)²(0.09)/0.0001 ≈ 11,128 ต่อกลุ่ม
      ตรงกับ “Minimum required samples at MDE 0.01 = 11128” ในกราฟสไลด์
    MDE ครึ่งหนึ่ง → ต้องใช้ n สี่เท่า (n ∝ 1/MDE²)

    07 A/A tests · trends & seasonality

    A/A test: ตั้งใจแบ่ง cookies เป็น control กับ control ให้เห็นหน้าเดียวกัน แล้ว plot การแจกแจงของผลต่าง conversion — บอกว่า “ความต่างจากความบังเอิญล้วน ๆ” ใหญ่แค่ไหน (ใช้เลือก MDE และประมาณ pooled variance เชิงประจักษ์) และเช็กว่าระบบแบ่งกลุ่มทำงานถูก

    ควรได้ ~5% — ถ้ามากกว่านี้มาก แปลว่าระบบแบ่งกลุ่ม/tracking ผิด หรือข้อมูลไม่อิสระ

    Trends & seasonality

    รันจนกว่าจะครบ sample ที่คำนวณไว้ หรือครบทุก seasonality ที่รู้ แล้วแต่อันไหนนานกว่า — เช่นอย่างน้อย 1 สัปดาห์เต็มให้มีคนซื้อวันหยุด · ใช้ข้อมูลปีต่อปี (year-on-year) normalize เพื่อตัด trend

    Design journal: สมมติ MDE 1% จาก A/A tests แล้วรันจนครบ n ต่อ variation และอย่างน้อย 1 สัปดาห์

    08 ⑤ Run & monitor — Do not peek — keep your tests in line

    ถ้า H₀ จริง test แบบ frequentist สัญญาว่า false positive rate ≤ α — แต่ถ้าแอบดูผลหลายครั้งก่อนครบ n แล้วหยุดทันทีที่ significant สัญญานั้นพัง สไลด์: จำลอง 1,000 ครั้ง กลุ่มที่ไม่ต่างจริงถูกปฏิเสธ H₀ ด้วยการ peek ถึง 22.4% (ดูตอนจบครั้งเดียวได้ 6.4%)

    Sanity check — ทุกอย่างเป็นไปตามแผนไหม

    • กลุ่มถูกแบ่งตามที่ตั้งใจ? cookie เดียวเห็นทั้งสองแบบ = หายนะ
    • ตัวแปรที่คุมถูกคุมจริงไหม
    • Twyman's law: สถิติที่ดูน่าสนใจ มักเป็นความผิดพลาด — dev ใช้ random() แทน cookie-based split, variation หนึ่งโหลดไม่ขึ้น, tracking พัง
    • Tracking: เว็บผ่าน Google Tag Manager → BI / ads platforms · แอปผ่าน Firebase SDK

    Post-test monitoring

    • Novelty effect: ลูกค้าสนใจเพราะของใหม่ แล้วค่อย ๆ กลับไปเท่ากลุ่ม control
    • หลังตัดสินใจแล้ว เก็บ control ไว้ส่วนเล็ก ๆ (เช่น 10%) เพื่อยืนยันผลระยะยาว
    Design journal: เช็กว่า cookie เห็นเฉพาะ variation ของตัวเอง · หลังจบเก็บ 10% ไว้ที่ control

    09 ⑥ Analyze results — multiple test corrections — we are running a business after all

    ทดสอบมากพอ ยังไงก็เจอ significant: รัน test จากข้อมูลรายวัน 60 ครั้ง จะมี ~3 ครั้งปฏิเสธ H₀ แม้สองกลุ่ม conversion เท่ากันจริง (60 × 0.05 = 3)

    1. FWER = P(มี false positive ≥ 1 จาก m tests) = 1 − (1 − α)m
      ถ้า test อิสระกัน
    2. Bonferroni: αeach = αoverall/m → 0.05/10 = 0.005
      ง่ายและ conservative มาก
    3. Šidák: αoverall = 1 − (1 − αŠidák)m ⇒ αŠidák = 1 − (1 − αoverall)1/m = 1 − 0.951/10 = 0.005116
      สไลด์เขียนตัวอย่างเป็น “1 − (1−0.05)^10” แต่ตัวเลข 0.005116 มาจากยกกำลัง 1/10 (ถ้ายกกำลัง 10 จะได้ 0.401)
    4. มีวิธีที่ conservative น้อยกว่า เช่น Benjamini–Hochberg (คุม false discovery rate)

    Take actions; understand the risks

    A/B test มีไว้ช่วยตัดสินใจในโลกจริง ไม่ใช่ให้เราเป็นเครื่องคิดเลข — ประเมินว่าถ้าผิด (false positive/negative) จะเสียอะไร · ส่วนใหญ่ control ชนะ สิ่งสำคัญคือเราตอบสนองอย่างไร

    Design journal: รัน test ครั้งเดียวตอนจบ แล้วใช้ซองสีที่ชนะ

    10 Limitations & design journal ฉบับเต็ม

    เมื่อไหร่ ไม่ควร ทำ A/B test

    • สิ่งที่สรุปเป็น metric ไม่กี่ตัวไม่ได้ (“ผู้ใช้มีความสุขไหม?”)
    • ของใหม่หมด เทียบ apple-to-apple ไม่ได้ → survey, focus group, design thinking
    • ผลล่าช้า (การซื้อซ้ำรอบ 3 เดือน)
    • เหตุการณ์ครั้งเดียว (11.11, Black Friday ไม่เคยเหมือนกัน)
    • แบ่งกลุ่มอิสระไม่ได้ (layout ร้านสาขาเดียว)

    A/B testing in the wild — บทเรียน

    • เข้าใจธุรกิจของตัวเอง
    • Tracking, tracking, tracking
    • ทำครบกระบวนการสักรอบ สำคัญกว่าทำทุกขั้นให้สมบูรณ์
    • ระบุ assumption ให้ชัด และเตรียมรับความเสี่ยง
    • Control ชนะบ่อย — สำคัญที่การตอบสนอง
