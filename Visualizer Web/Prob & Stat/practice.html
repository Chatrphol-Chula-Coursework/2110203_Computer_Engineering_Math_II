  1. เกณฑ์เลือก metric: (1) วัดสิ่งที่ treatment ตั้งใจเปลี่ยน (2) ไม่ถูก treatment “บิด” โดยตรง (3) variance ต่ำ → ใช้ sample น้อยกว่าในการเห็นผล (power สูง) (4) ไม่ขึ้นกับประเภท/คุณภาพโพสต์มาก
    variance ของ metric กำหนด sample size: n ∝ σ²/Δ²
  2. Comments ✗ — ถูก treatment ปนโดยตรง: ลิงก์อยู่ในคอมเมนต์ → คนเปิดคอมเมนต์มากขึ้น และเจ้าของโพสต์เองก็คอมเมนต์ลิงก์ · ยังผันผวนสูงสุด (CV ≈ 1.0: โพสต์ดราม่า Saudi 2,030 vs Are-Am-Eat 103)

  3. Reactions ✗/△ — รวม comments อยู่แล้ว จึงปนเหมือนกัน และขึ้นกับคุณภาพโพสต์ (23k/22k สำหรับโพสต์คุณภาพต่ำ)
  4. Likes / Shares △ — ขึ้นกับประเภทโพสต์มาก (likes กีฬา ~2.2k vs รีวิว ~1.1k, shares รีวิว 3–5k vs กีฬา ≤1.2k) → ต้อง stratify ตามประเภท ใช้เป็น guardrail ได้
    ถ้าสุ่มแล้วได้ประเภทไม่สมดุล ผลจะเพี้ยน
  5. “Read more” clicks ✓ — นิ่งที่สุด (1.0–1.2k ทุกโพสต์, CV ≈ 6.7%) ไม่ขึ้นกับประเภทหรือคุณภาพ และสะท้อน reach × ความสนใจ ซึ่งคือสิ่งที่ algorithm ลดลง
    variance ต่ำ = sensitivity สูง → เห็นผล 10% ได้ด้วยโพสต์ไม่กี่อัน
  6. Primary metric: “Read more” clicks ต่อโพสต์ (ใน 24 ชม.) — ถ้าเก็บได้ ให้ใช้คลิกลิงก์ / impressions (CTR) ซึ่งตรงเป้าหมายธุรกิจที่สุด · guardrail: likes, shares
    ใช้ข้อมูลวันแรกพอ เพราะ 99% ของ views เกิดในวันแรก

W2 ควรทำการทดลองอย่างไร — การแบ่ง A/B และสิ่งที่ต้องคุม

  1. หน่วยของการสุ่ม = โพสต์ (ไม่ใช่ผู้ใช้) — Hamtaro คุมไม่ได้ว่าผู้ใช้คนไหนเห็นอะไร platform เป็นคนกระจาย
    A = ลิงก์ในโพสต์ (control), B = ลิงก์ในคอมเมนต์ (treatment)
  2. Blocking / stratify: จับคู่โพสต์ที่คล้ายกัน (ประเภทเดียวกัน คุณภาพเดียวกัน) แล้วสุ่มว่าอันไหนได้ A อันไหนได้ B
    ลด variance จากประเภท/คุณภาพ และกันไม่ให้ treatment ปนกับประเภทโพสต์ (confounding)
  3. คุมเวลา: โพสต์ทั้งคู่ช่วงพักเที่ยงของวันเดียวกัน (หรือสลับ A/B ทุกวันแบบสุ่ม) · คุมจำนวน/ขนาดรูป ความยาว และตัดโพสต์คุณภาพต่ำจาก junior writer หรือให้กระจายเท่ากันสองกลุ่ม
    ผู้ใช้เข้าช่วงเที่ยง → เวลาโพสต์มีผลต่อ reach
  4. ค่าที่ monitor: “Read more” clicks (หรือ CTR) ของแต่ละโพสต์ ณ 24 ชม. หลังโพสต์ → ได้ 1 ค่าต่อโพสต์ · เปรียบเทียบด้วย two-sample t-test (หรือ paired t-test ถ้าจับคู่)
  5. Assumptions: algorithm คงที่ระหว่างทดลอง · โพสต์แต่ละอันอิสระกัน (ไม่ดึง traffic กัน) · ผู้ติดตามเดิมไม่เปลี่ยนมาก · metric ประมาณ Normal (CLT จากผู้ใช้จำนวนมาก)

W3 Stopping criterion ถ้ายอมรับการปรับปรุงอย่างน้อย 10% — power analysis

  1. Read more ก่อนเปลี่ยน: 1.1, 1.2, 1.0, 1.1, 1.2, 1.1 (k) → x̄ = 1.117k , s = 0.0753k
    ใช้ข้อมูลเก่าประมาณ σ
  2. หลัง algorithm ใหม่ (ลด 30%): μ ≈ 0.782k , σ ≈ 0.0527k
    assumption: ลดเป็นสัดส่วน → CV เท่าเดิม
  3. Δ = 10% × 0.782k = 0.0782k
    minimum detectable effect
  4. H₀: μB − μA ≤ 0 , HA: μB − μA > 0 · α = 0.05 (one-sided), power 0.8
    สนใจเฉพาะว่า B ดีขึ้น
  5. n ต่อกลุ่ม = 2(zα + zβ)² σ²Δ² = 2(1.645 + 0.842)²(0.0527)²(0.0782)² = 5.6 → 6 โพสต์ต่อกลุ่ม
    ปัดขึ้น · σ ประมาณจากแค่ 6 โพสต์และใช้ t แทน z จริง → เผื่อเป็น 8 ต่อกลุ่มจะปลอดภัยกว่า
  6. กฎหยุด: โพสต์ครบ n ต่อกลุ่ม (แต่ละโพสต์เก็บผล 24 ชม.) แล้วทดสอบครั้งเดียว: two-sample t-test, df = 2n − 2 = 10, ปฏิเสธ H₀ ถ้า t > t0.05,10 = 1.812 และ ผลต่างที่ประมาณได้ ≥ 10%
    ห้ามหยุดก่อนเพราะเห็นผลดี (peeking → false positive)
ลองตั้ง CV = 100% (ถ้าใช้ comments เป็น metric) → ต้องใช้โพสต์มากกว่าร้อยเท่า นี่คือเหตุผลเชิงตัวเลขของ W1

W4 ถ้า Elon Mark เปลี่ยน algorithm ทุกวัน — non-stationarity

ยังใช้ได้ไหม → ไม่ได้ทั้งหมด

  • ผลของ treatment ปนกับผลของ algorithm แต่ละวัน (confounded with time) — ถ้า A ส่วนใหญ่อยู่วันที่ algorithm ใจดี ก็ชนะโดยไม่เกี่ยวกับตำแหน่งลิงก์
  • σ ที่ใช้คำนวณ sample size ไม่คงที่ → power analysis ผิด
  • ผลที่ได้อาจใช้ไม่ได้กับ algorithm ของวันพรุ่งนี้

ทำอย่างไรแทน

  • Block by day: ทุกวันโพสต์ทั้ง A และ B (สุ่มลำดับ/ช่วงเวลา) แล้วใช้ paired t-test บนผลต่างรายวัน — algorithm ของวันนั้นหักล้างกันเอง
  • หรือใช้ multi-armed bandit (ε-greedy / Thompson sampling, ให้น้ำหนักข้อมูลล่าสุดมากกว่า) ที่ปรับตัวต่อเนื่องเมื่อสภาพแวดล้อมเปลี่ยน
  • ติดตามผลระยะยาว ไม่ตัดสินจากการทดลองครั้งเดียว

W6 ข้อบกพร่องของการทดลองนี้ — สิ่งที่ไม่ได้ควบคุม

Confounding ด้านเวลา

  • ไปแต่ละร้าน “ต่างเวลาของวัน” — ช่วงเร่งด่วน (เช้า/เที่ยง) คิวยาวกว่า ถ้าร้าน 1 บังเอิญถูกไปช่วงคนเยอะมากกว่า ร้าน 1 ก็ดูช้ากว่าโดยไม่ได้ช้าจริง
  • 10 วันต่างกัน (วันจันทร์ vs ศุกร์, วันฝนตก, โปรโมชัน)

อื่น ๆ

  • ไม่ได้สุ่มลำดับ/ช่วงเวลา และไม่ได้จับคู่เวลาเดียวกันระหว่างสองร้าน
  • ไม่ได้คุมเมนูที่สั่ง (เมนูซับซ้อนนานกว่า), พนักงาน/กะ, ระยะทางเดินไปร้าน
  • นิยาม “order time” ไม่ชัด (รวมเวลาต่อคิวไหม?), วัดเป็นนาทีเต็ม (rounding)
  • n = 5 ต่อร้าน → power ต่ำมาก · observer bias (Noppo จับเวลาเอง)

W7 ทำ hypothesis test กับข้อมูลนี้ — two-sample t-test

  1. H₀: μ₁ = μ₂ (สองร้านเร็วเท่ากัน)   HA: μ₁ ≠ μ₂
    two-sided — ก่อนเก็บข้อมูลไม่รู้ว่าร้านไหนเร็วกว่า
  2. Test: independent two-sample t-test (ไม่รู้ σ, n เล็ก, สองกลุ่มไม่ได้จับคู่เพราะไปต่างเวลา) · assumption: แต่ละครั้งอิสระ, ประมาณ Normal, variance ใกล้กัน
    ถ้าจับคู่เวลาไว้จริงจะใช้ paired t-test
  3. Null distribution: t ~ tdf , df = n₁ + n₂ − 2 = 8
    pooled variance
  4. sp² = 4(0.7) + 4(0.8)8 = 0.75 , SE = √(0.75 (1/5 + 1/5)) = √0.3 = 0.548
  5. t = 1.8 − 1.60.548 = 0.365 , p-value = 0.72
  6. critical (α = 0.05, two-sided): t0.025, 8 = 2.306 → |0.365| < 2.306
    ในตารางท้ายข้อสอบ 2024 ค่านี้อยู่ช่องที่ป้ายว่า 0.01 (ป้ายเลื่อน)
  7. ไม่ปฏิเสธ H₀ — ไม่มีหลักฐานว่าสองร้านเร็วต่างกัน
    (ถ้าคิดแบบ paired: t = 0.343, df = 4, p = 0.75 — สรุปเหมือนกัน)

W7′ Familiarity กับ GenAI มีผลต่อการจับโค้ด AI ไหม — ชุดที่ 3: Great Teacher Oxnard

EducatorCorrect /5Familiarityสอนวิชาเขียนโปรแกรม?
  1. แบ่งกลุ่ม: familiarity สูง (≥ 4) = E2–E7, E9 → 34/35 ข้อ (97.1%) · ต่ำ (≤ 3) = E1, E8, E10 → 9/15 ข้อ (60%)
    แต่ละระดับมีคนน้อยมาก จึงรวมเป็นสองกลุ่ม
  2. H₀: phigh = plow   HA: phigh > plow
    one-sided: คาดว่าคุ้นเคยมากกว่าจะจับได้ดีกว่า
  3. Two-proportion z-test: p̂ = 43/50 = 0.86 , SE = √(0.86 · 0.14 (1/35 + 1/15)) = 0.1071
    pooled p ใต้ H₀
  4. z = (0.971 − 0.600)/0.1071 = 3.47 → p ≈ 0.0003 < 0.05
    แต่ n(1 − p̂) ของกลุ่มต่ำ = 15 × 0.14 = 2.1 < 5 → normal approximation ไม่ค่อยน่าเชื่อ → ใช้ Fisher's exact test: p = 0.0018 (two-sided) ยัง significant
  5. ผล: มีความสัมพันธ์อย่างมีนัยสำคัญ (Spearman ρ = 0.64 ระหว่าง familiarity กับคะแนน, p = 0.046)
  6. ข้อควรระวัง: (1) n = 10 คน — ผลถูกขับด้วย E8 คนเดียว (familiarity 1, ถูก 1/5) ตัด E8 ออกแล้วความต่างเล็กลงมาก (2) 5 ข้อของคนเดียวกันไม่อิสระกัน (3) Confounding กับวิชาที่สอน — E8 ทั้งไม่คุ้น AI และไม่ได้สอนเขียนโปรแกรม → แยกไม่ออกว่าเป็นผลของอะไร (4) correlation ≠ causation

W8 วิชาที่สอนมีผลไหม — confounding

  1. แบ่ง: สอน Programming / Software Engineering / Data Structures = E2, E3, E4, E6, E7, E10 → 30/30 (100%) · วิชาอื่น (Architecture/OS, Database/Visualization/Web, Linear Algebra/Stats) = E1, E5, E8, E9 → 13/20 (65%)
    นิยามกลุ่มต้องประกาศก่อนดูผล
  2. Fisher's exact test: p = 0.0008 → ต่างอย่างมีนัยสำคัญ
    z-test ใช้ไม่ได้ เพราะกลุ่ม programming ผิด 0 ข้อ
  3. แต่สรุปเชิงเหตุไม่ได้: ทุกคนที่สอนเขียนโปรแกรมมี familiarity ≥ 3 ส่วนคนที่ตกมากที่สุด (E8, E1) ทั้งไม่สอนโปรแกรมและคุ้น AI น้อยกว่า → สองปัจจัยซ้อนกัน (collinear) ด้วยข้อมูล 10 คนแยกผลไม่ได้
    E5 (Database/Web) ถูก 5/5 ทั้งที่ไม่ได้สอน programming ตรง ๆ — ความหมายของ “วิชา” ยังกำกวม
  4. ต้องการ: ครูมากขึ้น ที่มีทุกคู่ผสม (สอนโปรแกรมแต่ไม่คุ้น AI, คุ้น AI แต่ไม่สอนโปรแกรม) แล้วใช้ stratified analysis / logistic regression

W9 ครูจับโค้ด AI ได้ “reliable” ไหม — นิยามก่อน แล้วค่อยทดสอบ

  1. นิยาม reliable (assumption): ความแม่นยำ ≥ 90% เพราะการกล่าวหาผิด (false positive) มีผลร้ายแรงต่อนักเรียน · อย่างน้อยต้องดีกว่าการเดา (50% — เลือก 1 จาก 2)
    ผลสรุปเปลี่ยนตามนิยาม จึงต้องระบุ
  2. ดีกว่าเดาไหม: H₀: p = 0.5 , HA: p > 0.5 → z = (0.86 − 0.5)/√(0.25/50) = 5.09 , p ≈ 10⁻⁷
    ดีกว่าเดาแน่นอน
  3. 95% CI ของความแม่นยำรวม: 0.86 ± 1.96√(0.86 · 0.14/50) = 0.86 ± 0.096 = [0.764, 0.956]
    คร่อม 0.9 → ยืนยันไม่ได้ว่าถึง 90%
  4. ความแปรปรวนระหว่างครูสูงมาก: 7 คนถูก 100% แต่ E8 ถูกแค่ 20% (แย่กว่าเดา) · Q1 ถูกแค่ 7/10
    “ครูโดยเฉลี่ย” ≠ “ครูทุกคน”
  5. Validity ของการทดลอง: เป็นแบบ forced-choice เป็นคู่ (รู้ว่าหนึ่งในสองเป็น AI) ซึ่งง่ายกว่าความจริงมาก — ในห้องเรียนครูเห็นทีละงาน ไม่มีคู่เทียบ · มีแค่ 5 ข้อ, AI ตัวเดียว, นักเรียนจริงแก้โค้ด AI ได้
    ผลจึงประเมินความสามารถจริง “สูงเกินไป”
  6. สรุป: จับได้ดีกว่าเดามาก แต่ยังไม่ reliable พอจะใช้ลงโทษนักเรียน
    นึกถึงข้อ 1.4 ของข้อสอบ: ถ้าคนโกงมีน้อย (base rate ต่ำ) แม้ตรวจแม่น 90% ผลบวกจำนวนมากจะเป็นการกล่าวหาผิด
ถ้าครูตัดสินทีละงาน: P(ใช้ AI จริง | ครูบอกว่าใช้) ด้วย Bayes

W10 คำแนะนำให้ Oxnard — จากผล W7–W9

อย่าพึ่งการ “ดูด้วยตา” อย่างเดียว

  • ความแม่นยำยังไม่ถึงระดับที่ใช้ลงโทษได้ และ base rate ทำให้ false accusation สูง
  • ถ้าต้องตรวจ ให้ครูที่สอนโปรแกรม/คุ้น GenAI เป็นคนตรวจ และใช้หลายคนตรวจร่วม (majority vote ลด error)

ออกแบบการประเมินใหม่

  • สอบเขียนโค้ดในห้อง / สอบปากเปล่าให้อธิบายโค้ดตัวเอง (viva)
  • ให้ส่ง version history (git commits) และงานทีละขั้น
  • โจทย์เฉพาะบริบทห้องเรียน หรืออนุญาตใช้ AI แต่ต้องระบุและวิเคราะห์ผลลัพธ์
  • เก็บข้อมูลเพิ่ม: ครูมากขึ้น ข้อมากขึ้น ทดสอบแบบไม่มีคู่เทียบ (ใกล้ความจริง) ก่อนตัดสินนโยบาย
